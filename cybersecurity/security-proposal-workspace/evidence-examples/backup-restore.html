These references identify fictional records. The reassessment models a reviewer accepting a restore test record. The scenario includes no production or cloud restore job.

What a reviewer checks

  1. Scope and protection. Check which campaign files and systems are backed up, which are excluded, and whether access to the backups is restricted.
  2. Restore point and destination. Identify the backup copy and when it was taken. Restore to an isolated test location so the exercise leaves the source files intact.
  3. Job outcome. Record when the restore started and finished, the job result, and any errors. Compare the chosen restore point and elapsed recovery time with agreed recovery objectives where they exist.
  4. Restored content. Open the restored file to verify it is usable. Compare its SHA-256 fingerprint with the expected version from the same restore point if available. A matching sample confirms the compared bytes for that file.
  5. Ownership and review. Identify who ran the exercise, who owns follow-up work, and who reviewed the evidence and accepted or rejected the claim.

REQ-015 tracks a separate check of backup integrity before restoration. A post-restore comparison supports the recovery exercise for REQ-010. REQ-015 still needs its own evidence.

Assessment progression

  1. Original assessment. EV-010 is already linked and reviewed. CTL-010 is recorded as partial, so REQ-010 needs work.
  2. Action ready. ACT-008 moves from planned to ready for review. The requirement still needs work because the control remains partial.
  3. Reassessment. The scenario records CTL-010 as implemented and updates the synthetic evidence reference and review date. REQ-010 becomes a supported draft when the recorded inputs pass the assessment checks.

The workspace evaluates control and evidence metadata. A human reviewer examines the restore record and decides whether it supports the claim for the stated scope.
