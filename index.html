        From request to reviewed reply

        1. Read. Start with one fictional request and the facts the requester supplied.
        2. Route. Follow the reported symptoms in order. Set aside general advice and resolved incidents when their wording makes that clear. Keep failures that return active. The technician chooses when multiple problems remain or the rules lack a supported category.
        3. Draft. Ask for the details still missing, then edit the reply in place.
        4. Review. A category change requires a fresh draft or confirmation that the current draft fits. Edits after review reopen that step.

        Linear search compares the target with each value in order. It stops at the first match or reaches the end of the list.

        Selection sort looks for the smallest remaining value, puts it in the next position, and repeats. The demo counts comparisons separately from steps such as placing a value.

        From topology to test

        1. Build. Connect three PCs and one web server to the switch. Assign each endpoint its own VLAN.
        2. Route. Trunk the four VLANs to R1, give each a gateway, and verify connectivity before filtering.
        3. Restrict. Allow Guest HTTP to the DMZ server and web replies back to Guest. Limit router SSH to the Admin PC.
        4. Verify. Compare the baseline with the filtered traffic. Try SSH from Admin and Staff using the same router address.

        The broader architecture design includes VPN access, IDS/IPS, SIEM, and a honeypot.

                    3. How many comparisons does selection sort make on an already sorted list?

                        The Workbench demo traces the algorithms in JavaScript. The C++17 command line program runs locally. Both implementations have their own tests.

                        JavaScript models the arithmetic instructions shown in the trace. The input range keeps the results within signed 32-bit limits.

                        The browser trace illustrates the planned policy. Packet Tracer will supply the observed results.

                        I coordinated the service transfer, set up the router and Wi-Fi, and verified basic internet access on both connection types. The cost comparison uses the previous monthly internet bill as its baseline.

                        I used my cell as the external endpoint so the checks exercised calls and texts between Zoom Phone and a separate mobile line.

                        The full tool runs locally in Python. This browser demonstration analyzes a separate six-ticket sample using JavaScript. It checks required fields, groups repeated subject wording, and flags resolved or closed tickets without notes. Repeated wording is a review candidate, not proof of the same root cause.

                        Built with HTML, CSS, and JavaScript. Published with GitHub Pages. The visual effects and project interactions run in the browser.

                        The JavaScript rules and sample tickets run in the browser. The demo keeps draft edits in memory and clears them when you reload. Replies stay in the demo.

                        The assessment engine runs locally in Python using the standard library. The published report is a fixed fictional example, not a live assessment service or a compliance determination.

                        The original desktop game uses Rust and ggez. This browser adaptation reimplements the game rules in Rust compiled to WebAssembly; JavaScript handles the browser display and controls. Closing the game resets the current session.

                        R validates the public CISA catalog and generates a monthly JSON snapshot. GitHub Actions checks daily; JavaScript displays the latest available snapshot and a bundled fallback when needed.
