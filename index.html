    Follow the practice guide ↗

    Adapted from my Computer Organization class project. The trace starts with the inputs already in ESI and EDI. Each operation copies ESI into EAX, performs its arithmetic, and saves the result.

    Division prepares EDX:EAX with CDQ. Then IDIV puts the quotient in EAX and the remainder in EDX.

    From topology to test

    1. Build. Connect three PCs and one web server to the switch. Assign each endpoint its own VLAN.
    2. Route. Trunk the four VLANs to R1, give each a gateway, and verify connectivity before filtering.
    3. Restrict. Allow Guest HTTP to the DMZ server and web replies back to Guest. Limit router SSH to the Admin PC.
    4. Verify. Compare the baseline with the filtered traffic. Try SSH from Admin and Staff using the same router address.

    The broader architecture design includes VPN access, IDS/IPS, SIEM, and a honeypot.

    The Questions Behind the Work

    1. Which index does linear search return when the target appears more than once?
    2. How does selection sort decide which value to place next?
    3. How many comparisons does selection sort make on an already sorted list?

    Search for 7 in 4 2 7 7 to see the first match at index 2 after three comparisons. Sort 4 2 7 and then 2 4 7 to see how this selection sort makes three comparisons in both cases.

    The Workbench demo traces the algorithms in JavaScript. The C++17 command line program runs locally. Both implementations have their own tests.

    JavaScript models the arithmetic instructions shown in the trace. The input range keeps the results within signed 32-bit limits.

    The browser trace illustrates the planned policy. Packet Tracer will supply the observed results.

    The full tool runs locally in Python. This browser demonstration analyzes a separate six-ticket sample using JavaScript. It checks required fields, groups repeated subject wording, and flags resolved or closed tickets without notes. Repeated wording is a review candidate, not proof of the same root cause.

    Built with HTML, CSS, and JavaScript. Published with GitHub Pages. The visual effects and project interactions run in the browser.

    A local JavaScript prototype using fictional tickets and rule-based matching. Draft responses require human review.

    The assessment engine runs locally in Python using the standard library. The published report is a fixed fictional example, not a live assessment service or a compliance determination.
